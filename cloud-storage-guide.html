The Big Picture

How cloud sync works in your app

Before touching anything, here's the full flow so you understand what each piece does. No jargon.

👤

User signs up / signs in

Firebase Auth creates an account and gives them a unique ID (UID). Your app stores a flag in their browser so they stay logged in.

↓ onAuthStateChanged fires automatically
☁️

App checks Firestore for their data

It looks for a document at war_room_data / <their-uid>. If found, loads it. If not, uses local data and pushes it up.

↓ every time they make a change
💾

App auto-saves to Firestore (debounced 1.2s)

After 1.2 seconds of inactivity, the full app state is written to their cloud document. The "● synced" indicator confirms it went through.

↓ when they open on another device
📱

New device signs in → cloud data loads instantly

Same UID, same Firestore doc. Their entire War Room is restored — businesses, tasks, P&L, goals, everything. No export/import needed.

Setup · Step 1 of 5

Open your Firebase project

You already have a Firebase project created (the config in your code references it). You just need to configure it correctly.

01

Go to the Firebase Console

Open in a browser — log in with the Google account that owns the project

Navigate to console.firebase.google.com and click on the project named createwarrom (that's what's in your app code).

⚠️

Don't see it? The project was likely created by a different Google account. Check which Gmail you used when you first set this up, or create a brand new Firebase project and paste the new config into your app.

Setup · Step 2 of 5

Turn on Email/Password sign-in

Firebase Auth is the gatekeeper — it handles accounts so you never touch passwords yourself. You just need to flip the switch.

02

Enable Email/Password authentication

In the Firebase Console left sidebar

Follow this path in the console sidebar:

Build→ Authentication→ Sign-in method tab→ Email/Password→ Enable (toggle on)→ Save

That's it for auth. Your app already handles the sign-up/sign-in forms — you're just telling Firebase "yes, allow this method."

💡

Optional for beta: You can also enable Google Sign-In here. Your app already has that button wired up — it just needs to be enabled in the console and you need to add your domain to the authorized domains list.

Setup · Step 3 of 5

Create the Firestore database

Firestore is where all user data actually lives. Think of it as a giant filing cabinet in the cloud — one folder per user.

03

Create your Firestore database

One-time setup in the console

Build→ Firestore Database→ Create database

You'll be asked two things:

1. Location: Pick the region closest to where most of your beta users will be. us-central1 is a safe default for US users. This cannot be changed later.

2. Start mode: Select Production mode. This locks everything down by default — you'll add the real rules in the next step. Do NOT pick test mode for a real launch (it makes all data publicly readable for 30 days).

🚫

Never use Test Mode for real users. Test mode turns off all security so anyone on the internet can read and delete every user's data. It's only meant for local dev experiments.

Setup · Step 4 of 5 — Most Important

Set Firestore security rules

This is the most critical step. Without proper rules, authenticated users could accidentally read each other's data. These rules lock each document to its owner.

04

Paste these rules into Firestore

Firestore Database → Rules tab → paste → Publish

In the Firebase Console, go to Firestore Database → Rules tab. Delete everything that's there and paste this exactly:

firestore.rules — copy this entire block
rules_version = '2';

service cloud.firestore {
  match /databases/{database}/documents {

    // war_room_data: each user can only read and write their own document.
    // No other user — or anyone unauthenticated — can touch it.
    match /war_room_data/{userId} {
      allow read, write: if request.auth != null
                         && request.auth.uid == userId;
    }

    // Block everything else by default.
    match /{document=**} {
      allow read, write: if false;
    }

  }
}

Click Publish. That's all. Here's what this does in plain English:

  • ✓
    Must be logged in — unauthenticated visitors can't read or write anything
  • ✓
    Can only access their own document — a user with UID abc123 can only touch war_room_data/abc123, not anyone else's
  • ✓
    Everything else is blocked — any other collection or path is a hard deny
🔒

This is the only Firestore config your app needs for beta. Your app's save/load code already targets the war_room_data/{uid} path exactly, so these rules match perfectly out of the box.

Setup · Step 5 of 5

Add your domain to Firebase Auth

Firebase blocks sign-in attempts from unknown domains as a security measure. You need to whitelist wherever your app is hosted.

05

Whitelist your app's domain

Authentication → Settings → Authorized domains

Authentication→ Settings tab→ Authorized domains→ Add domain

Add whatever URL your app is deployed to. Common examples:

warroom.app
www.warroom.app
your-project.vercel.app

localhost is usually already in the list by default (for your own testing).

⚠️

Deployed but sign-in fails? This is almost always the cause. Firebase will throw an "unauthorized domain" error if your live URL isn't on this list.

Validation

How to test it's working end-to-end

Do these steps in order before you invite any beta users.

T1

Test sign-up on your live URL

Not localhost — the actual deployed domain

Open your deployed app, click Cloud in the top bar, and create a new account with a test email. After sign-up, check Firebase Console → Authentication → Users — you should see the account appear within seconds.

T2

Add some data, check Firestore

Confirm the data is actually reaching the cloud

Add a business, a task, anything. Wait 2 seconds. Then open Firebase Console → Firestore Database → Data tab. You should see a war_room_data collection with a document named after your user's UID. Click it — your data should be there as a JSON blob.

💡

Sync indicator says "✕ sync failed"? Open browser DevTools (F12) → Console tab. The error message will tell you exactly what's wrong — most likely a rules mismatch or the database doesn't exist yet.

T3

Open a second browser / incognito / different device

The real cross-device test

Open your app in a fresh browser with no local storage (incognito works). Sign in with the same test account. Your data — every business, task, and setting — should appear within a few seconds. If it does, cloud sync is fully working.

T4

Test sign-in from a different account (privacy check)

Make sure users can't see each other's data

Create a second test account. Sign in as account B — you should see an empty War Room, not account A's data. This confirms the Firestore security rules are enforcing isolation correctly.

Costs

What does Firebase cost for a beta?

🆓

Firebase Spark (free) plan is more than enough for a beta. The free tier gives you:

• 1 GB of Firestore storage
• 50,000 reads / day
• 20,000 writes / day
• 10,000 deletes / day
• Authentication is always free

For context: a typical War Room user saving their full app state generates about 1 write every few minutes of active use. You'd need hundreds of very active daily users before approaching the free tier limits.

When to upgrade: Move to the Blaze (pay-as-you-go) plan only when you're past beta and hitting limits. There's no minimum charge — you only pay for what you use above the free tier.

Troubleshooting

Common errors and what they mean

!

PERMISSION_DENIED

The most common error

What it means: Your Firestore rules are blocking the write or read. Either the rules haven't been published yet, or the user isn't authenticated when the save fires.

Fix: Double-check Step 4 — make sure you clicked Publish after pasting the rules. Then check DevTools → Console for the exact UID being used.

!

auth/unauthorized-domain

Sign-in popup or button does nothing / throws error

What it means: The domain your app is on isn't in Firebase's authorized domains list.

Fix: Step 5 — add your exact domain (no trailing slash) to Authentication → Settings → Authorized domains.

!

Cloud button visible after sign-in / sync indicator never appears

UI not updating after auth

What it means: Firebase Auth initialized but the onAuthStateChanged listener didn't fire, usually because initFirebase() was called after the listener was registered, or the compat SDK scripts failed to load.

Fix: Open DevTools → Network tab and filter for "firebase". Make sure all 3 compat SDK scripts (app, auth, firestore) are loading with status 200. If any are blocked by an ad blocker or CSP header, the auth state listener won't run.

!

Data loads on sign-in but is stale / missing recent changes

Sync working but saves falling behind

What it means: The 1.2-second debounced save is being interrupted — user closed the tab before the timer fired, or a save error was silently swallowed.

Fix: Watch for "✕ sync failed" in the top bar. Also consider adding saveToCloud(true) to the browser's beforeunload event so a final save fires when the tab is about to close.

Launch Checklist

Your beta launch checklist for cloud sync

  • Firebase project createwarrom is accessible in your console
  • Authentication → Email/Password is enabled
  • Firestore database created in Production mode
  • Security rules published (the rules from Step 4 above)
  • Your live domain added to Authorized Domains
  • T1–T4 tests all passed on the live URL
  • Firebase API key restricted to your domain in Google Cloud Console (optional but recommended before public launch)
🚀

Once all six are checked — you're ready for beta users. They'll sign up, their data will sync to Firestore in real time, and they can open War Room on any device and pick up exactly where they left off. No exports, no imports, no local storage dependency.
